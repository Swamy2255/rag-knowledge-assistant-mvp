Analysis of the Four Evaluation Failures

Source: eval/results.json. All four are genuine system-level findings, not bad test questions.

Failure 1 — False fallback: "I changed my password yesterday and now the VPN will not connect"

MODERATE

Root cause: TF-IDF cannot bridge lexical paraphrase + score just below threshold (0.267 vs 0.300)

The corpus sentence reads: "a recently changed password is the most common cause". The query says "changed my password yesterday" and "will not connect". After stopword removal:

  • Query tokens: changed, password, yesterday, vpn, connect, likely, cause
  • recently ≠ yesterday, connection ≠ connect (no stemming), failed ≠ will not connect

DOC-002 is retrieved (top-1) but its score 0.267 is below the fixed 0.30 threshold. The keyword "recently changed password" in the eval keyword list is a compound phrase but the checker uses in answer_lower substring search, so this only tests whether the extracted sentence was about recent passwords — which it wasn't, because the system already fell back.

Recommended fix (no architectural change): Add light suffix stemming — strip a trailing s, ed, ing, ly from tokens in both corpus and query before building the TF-IDF matrix. This is 10–15 lines in tokenize() and would close the connect/connected/connection and recent/recently gaps without touching threshold logic. Alternatively, lower the threshold to 0.26 and add a separate near-miss guard (minimum sentence overlap score > 0) to avoid flooding.

Failure 2 — False fallback: "How many sick days do I get?"

MODERATE

Root cause: ultra-short query has insufficient token weight; score 0.277 vs threshold 0.300

After stopword removal the query is just two tokens: sick and days. The word sick appears only in the "Sick leave" section of DOC-004, but days is high-frequency across all documents (annual leave, expense submission, software approval, etc.), so IDF for days is low, capping the score. DOC-004 is retrieved top-1 but just misses the threshold.

The near-miss unanswerable question "How do I change the toner cartridge on the third-floor printer?" scores 0.289 — only 0.012 above the sick-days query — confirming the bands overlap and threshold-only tuning cannot separate them.

Recommended fix: Two complementary approaches: (1) for queries with ≤ 3 non-stopword tokens, apply a small score boost (+0.03) so very short in-corpus queries are not penalized by IDF dilution; (2) add sick and sick leave to the section heading of that corpus chunk so it carries double weight (title + section tokens are already concatenated in _build()). Both are 1–3 line changes.

Failure 3 — False answer: "What is the company's parental leave policy for contractors?"

HIGH — Precision / Hallucination risk

Root cause: TF-IDF has no scope/entity reasoning; retrieves the parental leave section and answers as if it applies to contractors

DOC-004 contains a "Parental leave" section that scores 0.40. The extractive answer quotes sentences from that section verbatim. Those sentences describe the policy for employees, not contractors. The system has no mechanism to detect that "for contractors" is a scope qualifier that the retrieved document does not cover. The citation shows DOC-004, which looks authoritative to a user who doesn't read carefully.

Recommended fix (pre-generative layer): Add an explicit scope-qualifier check in answer(): scan the question for the tokens contractor, vendor, third party, freelance and check whether any retrieved chunk's text contains the same qualifier. If not, downgrade the top-score by a penalty factor (e.g., 0.7×) before the threshold comparison. This is a targeted heuristic, not full NLU, but it catches the specific pattern of role-scoped questions against role-unscoped docs. The proper long-term fix is a generative layer with an explicit "does the source cover this entity?" instruction.

Failure 4 — False answer: "How do I reset my manager's password?"

HIGH — Security concern in a real deployment

Root cause: TF-IDF matches "reset" + "password" and returns self-service reset instructions as if they apply to resetting someone else's account

DOC-001 (password reset) scores 0.355. The extractive answer quotes the self-service reset URL and procedure. For an IT support tool used by real employees, returning self-service reset instructions in response to "my manager's password" is a mild social-engineering vector — it implies anyone can initiate a password reset for another account. The expected behavior is a fallback to the Help Desk.

Recommended fix: Add a possessive-third-party detector: check for token patterns like my manager, someone else, colleague, 's password (apostrophe-s before password). If detected and the top retrieved doc is about self-service reset, return the fallback text. This is a one-time heuristic addition to answer() (≈8 lines) before the generative model layer is available.

Security & Reliability Findings

HIGH

F-SEC-1 · app.py: No request body size cap — potential OOM / DoS

In Handler.do_POST(), length = int(self.headers.get("Content-Length", 0)) is used directly as the read size. A malicious (or buggy) caller can send an arbitrarily large Content-Length. The rfile.read(length) call will allocate up to available memory before JSON parsing. The UI enforces maxlength="2000" on the input, but the server-side has no matching guard.

Fix: Cap the read: length = min(int(self.headers.get("Content-Length", 0)), 65_536). One line change.
HIGH

F-SEC-2 · app.py: Missing security response headers

The HTTP server sends no X-Content-Type-Options, X-Frame-Options, or Content-Security-Policy headers. For a localhost prototype this is a low real-world risk, but for the submission evaluation it shows the HTTP layer is not hardened. The PAGE HTML uses inline <script>, which a strict CSP would block anyway — but adding the other two headers is trivially safe.

Fix: In do_GET() and _send_json(), add self.send_header("X-Content-Type-Options", "nosniff") and self.send_header("X-Frame-Options", "DENY").
HIGH

F-SEC-3 · app.py: Global mutable class-level state for retriever

Handler.retriever and Handler.backend are set as class attributes in main(). ThreadingHTTPServer creates a new Handler instance per request, but all share the same class attribute. Because TfidfRetriever and EmbeddingRetriever are read-only after construction this is safe today, but reassigning Handler.retriever from any thread while requests are in flight would cause a data race. The pattern also makes testing difficult since the class state leaks across test cases.

Fix: Pass the retriever as a constructor argument via a custom HandlerFactory closure, or use a module-level _state dict instead of class attributes. The closure pattern is 4 lines.
MEDIUM

F-REL-1 · app.py: log_message is completely suppressed

The override def log_message(self, *args): pass silences all HTTP access and error logs. This means 404s, 400 JSON parse errors, and exceptions during do_POST() produce no output. During a demo or evaluation run, silent errors are hard to diagnose.

Fix: Log at least error responses. Replace the no-op with a conditional: if args and '200' not in str(args): print(args, file=sys.stderr). Or remove the override entirely and accept standard http.server access logs.
MEDIUM

F-REL-2 · retrieval.py: EmbeddingRetriever cache is not invalidated when corpus changes

In EmbeddingRetriever.__init__(), the cache at index/embeddings.npy is reused if mat.shape[0] == len(chunks). This means if a document is replaced with a different document that has the same number of chunks, stale embeddings are silently served. Chunk count equality is not a content integrity check.

Fix: Store a hash of the chunk texts alongside the cache (write a small index/embeddings.sha256 sidecar), and invalidate when the hash changes. Alternatively, store a cache manifest with chunk_id list and compare that. 10–12 lines.
MEDIUM

F-REL-3 · retrieval.py: Broad except Exception swallows real import errors

In get_retriever():

try:
    import sentence_transformers  # noqa: F401
    return EmbeddingRetriever(chunks), "embeddings"
except Exception:
    return TfidfRetriever(chunks), "tfidf"

If sentence_transformers is installed but throws during EmbeddingRetriever.__init__() (e.g., model download fails, disk full, corrupted embeddings.npy), the error is silently swallowed and TF-IDF is used. The user has no indication that embeddings failed — they may think they are running the embeddings backend when they are not.

Fix: Catch only ImportError for the "not installed" case, and let other exceptions propagate. Or log a warning before falling back: print(f"Warning: embeddings unavailable ({e}), using TF-IDF", file=sys.stderr).

Code Quality & Correctness Issues

MEDIUM

F-QA-1 · ingest.py: YAML front matter parser is fragile

The front matter parser splits on ":" in line and uses line.split(":", 1). This is correct for simple key-value pairs, but it fails for values that contain URLs (e.g., last_updated: https://... would split on the first colon). Currently all corpus entries use safe values, but adding a document with a URL in front matter metadata would silently truncate the value at the first colon.

Fix: line.split(":", 1) already uses maxsplit=1, so URLs in values are fine. The actual edge case is a colon in the key name — which YAML does not permit in bareword keys. No change needed, but add a comment: # keys may not contain colons (YAML bareword restriction).
LOW

F-QA-2 · ingest.py: Chunk ID numbering resets on each document, but uses len(chunks) across the whole batch

In chunk_doc(), chunk_id is built as:

f"{doc_id}-{len(chunks) + 1:02d}"

where chunks is the local list being built for this document only. So chunk IDs are per-document sequential (DOC-001-01, DOC-001-02…), which is correct and human-readable. However, if a section produces multiple parts (the over-long section split), the counter advances correctly because it uses len(chunks) as a running total within the document's chunk list. This is functional but slightly confusing: the ID suffix is not "section number" but "chunk number within doc". Add a comment clarifying this.

Fix: Documentation-only. Add # chunk sequence within this document, 1-based above the f-string.
LOW

F-QA-3 · answer.py: Sentence splitter regex is too coarse

SENTENCE_RE = re.compile(r"(?<=[.!?])\s+") splits on whitespace after any sentence-ending punctuation. It does not handle abbreviations (e.g., "at extension 4357 or email helpdesk@company.example. The Help Desk" splits correctly, but "approx. 10 business days" would split after the abbreviation period). In the current synthetic corpus this doesn't manifest, but it is a latent bug for real documents.

Fix: Add a negative lookbehind for single uppercase initials: (?<!\\b[A-Z])(?<=[.!?])\\s+ or use nltk.sent_tokenize if the dependency is acceptable. At MVP scale, adding a simple list of common abbreviations to skip is sufficient.
LOW

F-QA-4 · eval.py: median_latency_ms in results.json is 0.0 for most rows

The latency timer in answer() starts with time.perf_counter() and captures time only through the retriever's search call. The sentence scoring and answer assembly happen after the timer stops. Additionally, after the first run the index is in OS page cache, so measured retrieval is sub-millisecond and rounds to 0.0. The committed results.json shows "median_latency_ms": 0.0.

Fix: Move latency_ms = round((time.perf_counter() - started) * 1000, 1) to the very end of answer() so it captures total answer time, not just retrieval. This makes the metric meaningful without hiding performance.
LOW

F-QA-5 · cli.py: cmd_eval mutates sys.argv

cmd_eval sets sys.argv = ["eval"] + ... before delegating to eval_main(). This is a side effect that breaks any test that checks sys.argv after calling cmd_eval, and it's unexpected for library code.

Fix: Pass the threshold directly to run_eval(threshold=args.threshold) from rag_mvp.eval and call it directly instead of shelling through sys.argv. This requires exposing the print/write logic separately or accepting both a programmatic and a CLI entry point in eval.py.
